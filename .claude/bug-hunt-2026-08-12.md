### C3. 超過 1024 公尺的區域,所有牆完全不衰減
**位置**:[propagationGL.js:2373-2374](../src/features/heatmap/propagationGL.js#L2373-L2374)
**驗證**:單方(程式碼 + 數值推算)
**成因**:`nGx/nGy` 被硬夾在 256,而 `cellM` 上限 4m(2372 行),所以加速格網最多覆蓋 **256 × 4 = 1024m**。`buildGrid` 的 bucketing 端有 clamp(2388/2390),超範圍的牆會被塞進最後一排 cell——**但 DDA 走到 x=1400m 時算出 `cx = 350`,`readGridCell(350, …)` 因超出 `uGridDims` 直接回 count=0**(359-365 行),而 DDA 又刻意不做邊界 bail(註解 455-458 說射線可能中途進入格網)。牆進了列表卻永遠讀不到。
**失效情境**:`sampleField.js:21-26` 註解明講支援「2 km campus」。2000×2000m、500 道牆的平面圖 → 格網只覆蓋 1024×1024m → x 或 y 超過 1024m 的區域,混凝土牆(12 dB × sec,最多 42 dB)**完全不衰減**,熱圖顯示成一片開放空間的綠色,實際是牆後死角。1500×800m 的場地損失 476m 寬的條帶。
**與 P1-9 的關係**:同屬「迴圈上限假設在極端幾何下不成立」,但成因不同——P1-9 是步數不夠,這條是格網根本沒蓋到。JS 參考實作(`propagation.js:70-86`)暴力掃全部牆,沒有這個問題 → 明確的 JS/GL 分歧。

### C4. Fence timeout 會讓 scissor 狀態永久污染 GL context,熱圖壞掉且無法自我復原
**位置**:[propagationGL.js:3135-3151](../src/features/heatmap/propagationGL.js#L3135-L3151)
**驗證**:單方(程式碼)
**成因**:`renderFieldAsync` 的 `gl.enable(SCISSOR_TEST)` 與 `gl.disable(SCISSOR_TEST)` 之間有 `await waitFence(...)`,而 `waitFence` 有三條 reject 路徑(2782/2793/2798:context lost、`WAIT_FAILED`、10 秒 timeout)。**沒有 try/finally**,reject 時 `disable` 被跳過,scissor 狀態永久留在 module-singleton context 上([sampleFieldGL.js:38-49](../src/features/heatmap/sampleFieldGL.js#L38-L49) 的 `glInstance`)。
**失效情境**:300 AP 場景在軟體渲染機上跑 `renderFieldAsync`(13 條 band),某條 band 超過 10 秒 → timeout → scissor 卡在最後一條 band(例如 `(0, 77, 121, 4)`)。之後:
- `renderAp` 只有第 77-80 列被寫入,其餘**保留上一次 draw 的殘值**(sized target 是 Map 重用的)→ 每個 AP 的 grid 有 95% 是別的 AP 的舊資料 → 熱圖出現橫向條紋鬼影
- `bakeLos` 只烤 4 列 → LOS 判斷錯誤 → 牆損耗被誤跳過
- `progFieldCoarse` 的 mask 只有 4 列是 1 → `FS_FIELD` 的 cascade early-exit 把 96% 格子判成 dead → **整張熱圖幾乎全空**

**最麻煩的部分**:`getGL()` 只在 `isContextLost()` 時才重建,而 fence timeout **不算 context lost** → 這個狀態不會自我復原,**必須重新整理頁面**。
**修法**:用 try/finally 保證 scissor 一定關閉。

## P1 — 影響正確性或使用者信任

### 7. 同一樓板有多個 FloorHole 時,GL 熱圖只有第一個洞豁免衰減(JS/GL 分歧)
**位置**:[propagationGL.js:2454-2461](../src/features/heatmap/propagationGL.js#L2454-L2461)(打包),shader 判斷在 687-688 / 1431-1432;JS 正確版本在 [propagation.js:298-302](../src/features/heatmap/propagation.js#L298-L302)
**驗證**:單方(程式碼逐式比對)
**成因**:`uploadSlabs` 把第一個洞打包成帶 `slabDb` 的 record、其餘洞打包成 `slabDb = 0`。Shader 每筆 record 獨立判斷 bypass,所以後續 `slabDb = 0` 的 record 不管是否 bypass 都貢獻 0,**無法**替第一筆豁免。註解宣稱「to preserve that semantics…」但實作達不到。
**失效情境**:同一層樓板畫兩座樓梯間,射線穿過第二個洞:JS(hover probe)給 0 dB 樓板衰減,GL 熱圖照加 12 dB(混凝土預設)→ 第二個洞下方熱圖明顯偏弱,且**hover 讀數與熱圖顏色互相矛盾**。

### 8. 編輯 FloorHole 後熱圖吃舊快取完全不更新
**位置**:[sampleFieldGL.js:171-186](../src/features/heatmap/sampleFieldGL.js#L171-L186)(async 版 402-415 同樣)
**驗證**:單方(程式碼)
**成因**:per-AP 輸出格快取的 `geomSig` 只涵蓋 boundary 的 `yM` 與 `slabDb`,**不含 `bypassHoles` 內容**;而 `uploadSlabs` 不會 bump `wallsVersion` 也不清 `outGridCache`(只有 `uploadWalls`/`uploadCorners` 會)。
**失效情境**:多樓層 + 反射開啟(走 per-AP 路徑),移動一個 FloorHole → 熱圖**完全不變**,直到剛好動了牆或 AP 才更新。hover probe 走 JS 即時算,於是再度與熱圖矛盾。

## P3 — Undo/Redo 時序與較小問題

### 17. 第一筆編輯後立刻 Ctrl+Z 完全沒反應
**位置**:[useHistoryStore.js:92-97](../src/store/useHistoryStore.js#L92-L97)
**成因**:`undoStack.length === 0` 的檢查在 `flushPending()` **之前**,pending 中的第一筆快照 undo 不到。
**失效情境**:新 session(或 loader 呼叫 `clearHistory()` 後)做第一筆編輯,在 debounce+idle 視窗(約 300-800ms,`DEBOUNCE_MS=300` + `requestIdleCallback timeout 500`)內按 Ctrl+Z → 什麼都不發生,`canUndo()` 同理回 false,工具列 undo 鈕是灰的。等快照 commit 後再按第二次才生效。
**修法**:把 flush 提到空檢查前(undo 內其他讀取都已是 flush 後重讀,順序安全)。

### 18. 編輯後 300ms 內按 Ctrl+Y 會靜默吃掉剛做的編輯,且 undo 堆疊順序錯亂
**位置**:[useHistoryStore.js:110-123](../src/store/useHistoryStore.js#L110-L123)(對照 undo 的 92-97 有 flush)
**成因**:`redo()` 不像 `undo()` 會 `flushPending()`。新編輯的快照還在 debounce 時 redoStack 尚未被 `pushToUndo` 清空,redo 照樣執行並用舊快照整層覆寫。
**失效情境**:Ctrl+Z(redoStack 得到一筆)→ 做新編輯 E → 300ms 內按 Ctrl+Y:整層 walls/aps 被覆寫回舊快照,**E 從畫布上消失**(標準行為應是「新編輯清空 redo,Ctrl+Y 無作用」);300ms 後 pending commit 又把「E 之前」的快照 push 到 undoStack 最頂,**undo 歷史從此非時序**——之後 Ctrl+Z 會先跳回 E 之前,再按一次反而讓被丟棄的 E 復活。
**修法**:redo 開頭同樣 `flushPending()`(flush 內的 `pushToUndo` 會清 redoStack,使此情境下 redo 正確變 no-op)。

### 23c. per-AP 快取簽章漏掉 parity 驗證用的兩個 flag,導致驗證工具永久回報綠燈
**位置**:[sampleFieldGL.js:171-186](../src/features/heatmap/sampleFieldGL.js#L171-L186)(async 版 402-415 完全相同)
**驗證**:單方(程式碼)
**這條的意義比它的直接影響大**,所以單獨說明。
**成因**:`geomSig` 收了 `maxReflOrder`、`enableDiffraction`、`freqOverrideN`、`cullFloorDbm`、`losFastMode`,但**沒收 `losEnabled` 與 `apGeoEnabled`**——而這兩個 opts 就在同一個函式的 137 行與 152 行被讀取,且直接改變數值輸出:
- `losEnabled` 切換「走 LOS 短路」與「跑完整 DDA 牆掃描」。程式碼自己的註解([propagationGL.js:130-132](../src/features/heatmap/propagationGL.js#L130-L132))說這是 "Bit-equivalent … **mod fp32 round-off**",也就是數值確實不同。
- `apGeoEnabled` 切換「shader 內 fp32 現算鏡像點」與「host 端 fp64 算好再降 fp32 的 baked 值」。反射路徑的 `reflPt`、`d1/d2`、相位 `tau` 全都不同。

**為什麼重要**:這兩個 flag 存在的目的**就是 parity 驗證**(152 行註解明寫 "lets callers turn this off (debug parity check vs unbaked path)")。開發者在 diff harness 先跑一次正常 render(baked,寫進快取),緊接著跑 `{ apGeoEnabled: false }` 想比對 unbaked 路徑 → hash 完全相同 → **`getCachedGrid` 命中,直接回傳剛才那份 baked grid**,`renderAp` 根本沒被呼叫。parity 檢查回報「差異 0.000 dB,完美一致」,但兩邊跑的是同一份資料。
**推論**:這很可能解釋了為什麼本報告中多條 JS/GL 分歧能長期存活——驗證工具對它們永久顯示綠燈。**建議把這條排在其他 GL bug 之前修**,否則修完無法信任驗證結果。

**驗證**:單方(程式碼 + 數值推算)
**成因**:`cameraCoverageRadii` 用 `Math.min(camera.fovDeg ?? 90, 120) * VFOV_RATIO / 2` 推垂直半視角。這個 `min(…, 120)` 對一般相機是合理防護,但**魚眼的 `fovDeg: 360` 是「水平環景」語意,不代表垂直也 360**;被夾成 120 後垂直半視角只剩 33.6°,而天花板魚眼實際接近 90° 的向下半球。
**數字**:FISHEYE 預設(fovDeg 360、z 3、tilt 85、range 9)→ `shallow = 85° − 33.6° = 51.4°` → `farM = min(9, 3/tan(51.4°)) = 2.39m`。若垂直半視角是真實的 ~90°,`shallow = −5° ≤ 2°` → `farM = 9m`。距離短算 **3.76 倍**,覆蓋面積 18.0 m² vs 規格 254.5 m² → **少算 93%**。
**失效情境**:放相機 → 型號選「Fisheye 魚眼 360°(天花板)」→ 面板「可視距離」顯示 9m,但下方「偵測覆蓋帶」顯示 **約 0.0–2.4m**;畫面上是直徑不到 5m 的小圓圈,放在挑高大廳中央看起來像壞了。連帶讓覆蓋率、盲區、重疊三份報表對魚眼佈點全部嚴重低估。`CameraListPanel.jsx:161` 的批次套用型號會一次打到多台相機。

**E1. `setSwitches` 從理論缺陷升為已觸發 bug**(高)
